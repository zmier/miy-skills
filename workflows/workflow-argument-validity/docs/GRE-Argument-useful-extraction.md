## 1. 对本 workflow 最重要的一句话

GRE Argument 的核心不是判断作者结论是否真实，也不是表达自己是否同意，而是：

```text
在作者给出的理由、证据和假设条件下，
这条论证线是否足以推出作者的结论。
```

这与 `workflow-argument-validity` 的核心问题完全一致：

```text
作者当前给出的论据、方法、数据、事实或例子
是否足以推出作者声称的结论。
```

因此，这份材料适合进入父 workflow，而不只是论效题子 workflow。

## 2. 任务边界

GRE Argument 明确排除三件事：

1. 不要求判断材料中的事实是否真实。
2. 不要求同意或反对作者立场。
3. 不要求表达自己的观点。

它要求做的是：

1. 看作者提出了什么结论。
2. 看作者用什么理由和证据支撑结论。
3. 找出作者必须依赖但没有证明的假设。
4. 判断推理步骤是否可靠。
5. 说明如果这些假设不成立，结论会如何受影响。

这可以直接变成本 workflow 的边界纪律：

```text
先验箭头，不先站队；
先问“推不推出”，不先问“结论真不真”；
先评价论证质量，不把自己的观点写成替代答案。
```

## 3. 读题动作

ETS 的读题动作可以抽象为四看：

| 动作 | 要看什么 | 对应本 workflow |
|---|---|---|
| 看证据 | 作者拿什么当 support / proof | evidence 节点 |
| 看明说 | 作者显性声称什么、总结什么 | claim / conclusion 节点 |
| 看暗含 | 作者默认了什么但没有证明 | hidden premise |
| 看必然推出 | 哪些内容是从明说内容中被作者继续推出的 | serial support / hidden support |

对应成操作流程：

1. 把原文拆成“证据、理由、结论、建议、预测”。
2. 找连接词，例如 therefore / thus / hence / in conclusion / consequently。
3. 为每一步建立 `A -> B` 箭头。
4. 对每条箭头补一句“这要成立，必须默认什么？”
5. 检查每个默认前提是否有证据支撑。

## 4. 关键概念

GRE 官方材料把 Argument 相关概念讲得很朴素，适合转成我们的基础词表。

| 概念 | 可迁移理解 | workflow 用法 |
|---|---|---|
| argument | 由 claim、reason、evidence 构成的一条论证线 | 论证树整体 |
| conclusion | 作者最终想让读者接受的判断 | root claim 或 subclaim |
| assumption | 作者必须默认、但未充分证明的前提 | hidden premise |
| alternative explanation | 能解释同一事实的竞争性解释 | 替代解释审查 |
| counterexample | 能反驳或削弱某个一般化判断的例子 | 反例压力测试 |
| evaluation | 对证据、理由和整体论证质量的评估 | arrow audit |

对 Skill 的启发：不要只输出“谬误标签”，而要输出：

```text
作者依赖了什么假设
这个假设为什么未被证明
如果假设不成立，上层结论会怎样
需要什么证据才能评估它
```

## 5. Argument 指令类型

PDF 中的 Argument 任务不是只有一种问法，而是有几类指令。它们非常适合补强我们的“输出目标识别”。

| GRE 指令类型 | 中文理解 | 对应 workflow 输出 |
|---|---|---|
| examine stated / unstated assumptions | 检查明示或暗含假设 | 假设表 + 断点段落 |
| what questions need to be answered | 需要回答哪些问题才能评估结论 | 评估问题清单 |
| alternative explanations | 有哪些替代解释可以解释同一事实 | 替代解释表 |
| evaluate recommendation / prediction / conclusion | 判断建议、预测、结论是否可靠 | 箭头审计 + 结论降调建议 |

这说明一个重要点：

```text
不是所有论证分析都应该写成“指出三四个谬误”。
有些任务更适合写成“需要补哪些信息 / 需要回答哪些问题 / 有哪些替代解释”。
```

这对学术审稿也很关键。很多审稿意见的最佳写法不是“作者犯了某某谬误”，而是：

```text
目前还需要回答 A/B/C，才能判断这个识别、机制或贡献声称是否成立。
```

## 6. 数字、百分比与统计材料

GRE 官方材料特别强调：遇到数字、百分比、统计数据时，不是做数学题，而是判断这些数字是否能支撑结论。

可迁移检查：

| 检查项 | 问题 |
|---|---|
| 绝对数与比例 | 百分比变化背后的基数是多少？ |
| 时间可比性 | 现在和过去的定义、口径、标准是否一致？ |
| 样本可比性 | 两次调查或两组数据是否来自可比样本？ |
| 替代解释 | 数字变化是否可能由天气、价格、时间、事件、政策、样本变化等原因解释？ |
| 指标到结论 | 指标变化是否真的代表作者声称的概念变化？ |

这可以补强父 workflow 的“数字陷阱”分类：

```text
数字不是证据本身；
数字只有在口径、基数、样本、时间和指标含义都匹配时，才可能成为有效证据。
```

学术审稿适配：

- 描述统计中的变量量纲是否清楚；
- 不同年份或来源的数据是否可比；
- 比例变量是否被误读为绝对数量；
- 回归系数、显著性、样本量是否足以支撑作者叙事；
- 宏观指标是否能代表微观构念。

## 7. 高分回答的结构

从评分标准和 reader commentary 可抽象出高分回答的共同特征：

1. 紧扣题目指令，不偏成自己的观点作文。
2. 能识别与任务最相关的论证环节。
3. 不只点名问题，还解释问题如何影响结论。
4. 组织清楚，有段落层级和过渡。
5. 每个问题都有足够展开，不只是问题清单。
6. 语言精确，但不依赖术语堆砌。

对应本 workflow 的输出要求：

```text
定位原论证 -> 指出隐含假设/缺口 -> 解释为什么该缺口重要 -> 说明需要什么证据或如何降调结论
```

## 8. 低分回答的典型失败

从 scoring guide 和 reader commentary 可以抽象出低分失败模式：

| 失败模式 | 表现 | 对本 workflow 的警告 |
|---|---|---|
| 不按指令 | 题目要求分析假设，却写成泛泛评论 | 输出前先识别任务类型 |
| 只贴标签 | 说“因果谬误”，但不解释具体断在哪里 | 谬误术语不能替代分析 |
| 误读假设 | 指出一个原文并不依赖的假设 | hidden premise 必须回扣原文箭头 |
| 缺少展开 | 只列问题，不说答案如何影响结论 | 每个问题要说明 implication |
| 自己站队 | 写自己的看法，而非评价作者论证 | 论证分析不等于观点作文 |
| 接受作者逻辑 | 复述或赞同原论证，没有审查箭头 | 必须独立做 arrow audit |

这可以转成 Skill 的 post-flight checklist：

```text
我是否回答了题目要求？
我是否只是在表达自己的观点？
我指出的假设是否真是作者结论所必需？
我是否解释了该假设失败时结论如何受影响？
我是否把谬误名词当成分析本身？
```

## 9. 两个官方练习题的可迁移启发

### Task 1: Corpora 健身水平、电脑使用与经济衰退

核心论证可以还原为：

```text
当前达标比例低于二十年前
+ 电脑拥有率高的地区健身水平也高
+ 健身相关支出异常低
-> 电脑使用不是健身下降原因
-> 经济衰退才是主要原因
-> 经济好转后健身水平会改善
```

可训练的断点：

1. 二十年前和现在的健身标准是否可比。
2. 电脑拥有率是否等于电脑使用时间。
3. 地区电脑拥有率高是否混入收入、教育、健身资源等因素。
4. 健身产品支出低是否一定由经济衰退造成。
5. 支出恢复是否必然带来健身水平恢复。

对学术审稿的启发：

```text
变量名看似对应 X，但操作化指标可能不是 X；
相关性反向不能直接排除因果关系；
一个替代解释能解释数据，不代表它就是主要解释。
```

### Task 2: Kali 雕塑、模具发现与收藏价值预测

核心论证可以还原为：

```text
发现头部和手部模具
-> 真人大小雕塑由真人模具制成
-> 不是由雕刻技术制成
-> 解释微型雕塑风格不同、工具少
-> 收藏价值会从真人大小雕塑转向微型雕塑
```

可训练的断点：

1. 发现头手模具，是否足以推出整个人体雕塑都用真人模具。
2. 模具可能是练习、辅助或局部工具，而非完整生产方式。
3. 微型雕塑风格不同是否只能由模具限制解释。
4. 工具少是否意味着没有使用工具，而不是工具腐坏、尚未发现或材料不同。
5. 收藏价值是否主要取决于制作方式，而非稀缺性、审美、材料、历史意义或市场偏好。

对学术审稿的启发：

```text
一个新发现只能支撑它实际覆盖的范围；
机制解释不能把“可能解释”写成“唯一解释”；
预测类结论需要额外市场/行为机制支撑。
```

## 10. 对 workflow-argument-validity 的建议补强

### 10.1 增加“任务指令识别”

在恢复论证树之前，先识别用户任务到底要求：

- 找假设；
- 提评估问题；
- 找替代解释；
- 审查预测；
- 审查建议；
- 写完整分析文本。

### 10.2 增加“假设影响链”

每个假设不要只写成一句话，而应写成：

```text
作者需要假设 H
H 支撑 A -> B
如果 H 不成立，B 至少需要降调为 B'
要验证 H，需要证据 E
```

### 10.3 增加“问题型输出”

审稿和论效中都应允许问题型输出：

```text
为了判断该结论是否成立，需要回答以下问题...
这些问题分别对应哪些论证箭头...
不同答案会如何改变结论可信度...
```

### 10.4 增加“数字统计审查”

把现有“样本 / 数字陷阱”拆得更可操作：

- 基数；
- 比例与绝对数；
- 时间口径；
- 样本口径；
- 指标含义；
- 替代解释；
- 从统计差异到概念结论的跳跃。

### 10.5 增加“评分/质量阶梯”

借 GRE scoring guide 的思路，把本 workflow 的 L4/L5 输出质量分为：

| 层级 | 判断 |
|---|---|
| 优秀 | 紧扣任务，抓住关键箭头，解释假设影响，组织清楚 |
| 合格 | 能指出相关问题，但展开不够深入或组织一般 |
| 弱 | 问题偏散，解释不充分，部分偏离任务 |
| 不合格 | 主要表达自己观点、复述原文或误读任务 |

## 11. 可直接迁移到 Skill 的检查清单

```text
1. 任务要求我做什么：找假设、提问题、找替代解释，还是评价结论？
2. 作者最终结论是什么？
3. 作者的主要证据和中间结论是什么？
4. 每条 A -> B 箭头需要什么隐含假设？
5. 哪些假设没有被证明？
6. 是否存在能解释同一事实的替代解释？
7. 数字、百分比、统计数据的基数、口径、样本、时间是否可比？
8. 如果某个假设失败，上层结论是变弱、需要降调，还是直接断裂？
9. 我的输出是否解释了“为什么推不出”，而不是只贴标签？
10. 我的段落是否回答了题目指令，而不是写成自己的观点文？
```
