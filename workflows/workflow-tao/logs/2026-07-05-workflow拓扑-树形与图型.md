## 当时总结

这个问题不是在补充一个普通分类，而是在质疑 `workflow-tao` 对 workflow 形态的默认假设。

当前 `workflow-tao` 中的描述更容易让人想到：

```text
workflow = 有主目标、有主干、有分支、有回退、有完成标准的复杂流程
```

这类 workflow 更接近树形或工序型 workflow。

但 `workflow-research` 暴露出另一类 workflow：主干不是一开始就知道，而是在多个候选路线、证据、文献、数据和外部偏好之间后验浮现。这类 workflow 更接近图型或探索型 workflow。

## Tree-like Workflow

tree-like workflow 的特征：

```text
总目标较清楚；
主干较早可见；
分支服务主干；
完成标准相对明确；
失败处理通常是回退、替代路线、红灯或兜底；
项目推进可以用阶段、工序、路线图描述。
```

典型例子：

```text
逆向工程数据采集：
抓接口
→ 分析参数
   → 静态分析
   → 动态分析
→ 写脚本
→ 工程交付
```

其他可能例子：

```text
格式转换 workflow；
论文返修 workflow；
代码修复 / CI 修复 workflow；
数据清洗和交付 workflow；
已确定目标的采集工程。
```

这类 workflow 可以有分支，但分支通常服务一个明确主干。

## Graph-like Workflow

graph-like workflow 的特征：

```text
总方向大致存在，但主干不一定一开始就知道；
多个候选节点 / 路线 / claim 并行生长；
节点之间会互相影响、合并、拆分、降级或重组；
完成标准是阶段性、竞争性、组合性的；
失败处理不只是回退，也可能是降级为机制、附录、弃用路线或另一项目；
最终主干往往是后验选择出来的。
```

以学术研究为例：

```text
候选问题 A
候选问题 B
候选问题 C
数据资产 D
文献线索 E
识别设计 F
期刊偏好 G
导师反馈 H
初步结果 I
```

它们不是简单线性关系，而是互相改写：

```text
数据 D 改变问题 A；
文献 E 否定问题 B；
初步结果 I 让 C 变成主线；
期刊偏好 G 让 A 降级为机制；
导师反馈 H 把两个 route 合并；
识别设计 F 暴露新的数据需求。
```

因此，graph-like workflow 更像：

```text
graph of candidate routes
每个 route 内部可能有 tree-like execution
route 之间竞争、合并、拆分、降级
```

## 关键洞见：图中的节点可以是树，也可以是图

用户特别指出：

```text
另一种是「近似于图」，但图中的每个节点内部可能是「树」（也可能是图）。
```

这是关键补充。图型 workflow 不是没有结构，而是结构分层：

```text
顶层：图
  多个 candidate routes / hypotheses / projects / claims 互相影响。

节点内部：树
  每条 route 内部可能有较清晰任务链：
  找文献 -> 找数据 -> 设计实验 -> 跑结果 -> 写解释。

节点内部也可能仍是图
  某条 route 内部继续分裂出多个子问题、子实验和候选解释。
```

因此更准确的抽象不是“树 vs 图”二选一，而是：

```text
有些 workflow 顶层就是树；
有些 workflow 顶层是图，但节点内部可以是树；
有些 workflow 顶层是图，节点内部仍然是图。
```

## 对 workflow-tao 的架构含义

`workflow-tao` 目前已经区分：

```text
工序型复合 Skill；
诊断路由型复合 Skill；
混合型 workflow。
```

但这个分类主要从“编排方式”看复杂性，还没有明确从“拓扑形态”描述 workflow：

```text
tree-like workflow；
graph-like workflow；
hybrid graph-of-trees workflow。
```

这次洞见提示：`workflow-tao` 应增加一个拓扑层判断。

创建或重构 workflow 型 Skill 时，除了问：

```text
这是工序型、诊断路由型，还是混合型？
```

还应问：

```text
它的顶层主干是否前置清晰？
它是否有多个候选路线并行竞争？
主干是预先给定，还是后验浮现？
节点内部是树形执行，还是继续保持图型探索？
完成标准是单一路径 green，还是 route portfolio 的阶段性收敛？
```

## 暂定草案规则

迁移状态：`draft-rule`。

可以先形成以下草案：

1. workflow 可按拓扑形态区分为 `tree-like`、`graph-like` 和 `hybrid graph-of-trees`。
2. tree-like workflow 适合阶段、工序、Red/Green、UAT、交付标准和失败回退。
3. graph-like workflow 适合 route portfolio、candidate claims、证据竞争、路线合并/拆分/降级和后验 paperization。
4. graph-like workflow 不能过早要求固定主干，否则会把探索性项目误工程化。
5. graph-like workflow 的节点内部仍可调用 tree-like 子 workflow，例如某条 research route 内部的数据清洗、实验、文献检索或写作任务。
6. workflow 父入口应声明自己的 topology 或至少说明主干是否前置清晰。
