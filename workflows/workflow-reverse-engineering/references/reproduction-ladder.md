# 复现阶梯

## 目的

逆向交付不只有“纯外部脚本复现”一种。父 workflow 使用复现阶梯来判断当前应该追求哪种 Green。

```text
R0 观察
→ R1 外部纯复现
→ R2 运行态函数代算
→ R3 离线 harness
→ R4 App/浏览器/进程运行态代发
→ R5 稳定服务化封装
```

越往上，越接近真实运行态；越往下，越独立、可移植、可解释。

## 阶梯定义

| 层级 | 名称 | 含义 | 适用场景 | 风险 |
| --- | --- | --- | --- | --- |
| R0 | 观察型证据 | 只能看到请求、响应、日志或 UI 变化 | 目标识别、候选筛选 | 不构成复现 |
| R1 | 外部纯复现 | 用 Python/Node/Go 等从零构造请求或算法 | 参数和算法已解释清楚 | 容易漏环境态 |
| R2 | 运行态函数代算 | 在目标运行时里调用已定位函数生成签名/密文 | 算法强依赖运行时但入口清楚 | 不等于算法本体已解 |
| R3 | 离线 harness | 在可控离线环境加载目标逻辑 | native/wasm/库函数可被宿主调用 | 补环境成本可能很高 |
| R4 | 运行态代发 | 借真实 App/浏览器/进程状态发起业务动作 | 账号态、设备态、连接态、风控态难外移 | 要严格限速和边界 |
| R5 | 稳定服务化 | 把 R2/R3/R4 包成受控 CLI/RPC/服务 | 需要重复低频调用或团队协作 | 需要治理、日志、脱敏、安全边界 |

## 选择规则

优先尝试 R1，但不要迷信 R1。

当以下条件出现时，考虑上移：

- 参数依赖设备态、账号态、连接态或长期 session；
- 算法依赖 native runtime、浏览器对象、系统 API、TEE 或真实进程初始化；
- 纯外部复现成本明显高于运行态代算；
- 服务端接受的是“真实运行态 envelope”，不是单个签名参数；
- 研究目标是阶段性交付，而不是完全还原算法。
- 目标已经从“解释一个参数”变成“低频稳定完成业务动作”或“构建可追溯语料库”；
- 外部 replay 成本主要来自账号态、设备态、风控态和连接态，而不是业务参数本身。

R4 不是 R1/R3 的失败品，而是另一类 Green：当目标系统本来就以 App、浏览器或进程运行态为安全边界时，正确交付可能是“受控运行态代发 + 证据/限速/落盘”，而不是强行剥离所有环境态。

## 平台映射

| 层级 | Android 例子 | JS 例子 |
| --- | --- | --- |
| R1 | Python 构造签名和请求 | Node/Python 复现 JS 算法 |
| R2 | Frida RPC 调 Java/JNI 方法 | 浏览器 console/extension/automation 调页面函数 |
| R3 | Unidbg 跑 so | Node vm、jsdom、wasm runtime |
| R4 | App 运行态代发 RPC/bridge | 浏览器自动化带真实 cookie/localStorage 发请求 |
| R5 | Xposed/Sekiro、受控 RPC 服务 | 本地浏览器代理服务、受控 headless session |

## 证据要求

每次选择复现层级时，要记录：

- 为什么当前层级足够或不够；
- 输入从哪里来；
- 输出如何验收；
- 是否依赖真实账号、设备、浏览器 profile、session 或外部服务；
- 能否迁移到新样本；
- 是否只是 `structural-green`，还是已经 `forward-test-green`。
- 如果选择 R4，必须声明 `externalRequestSentByPython=false` 或等价边界，说明请求实际由目标运行态发出。
- 如果进入批量/语料工程，必须额外声明覆盖率、服务端窗口、限速策略、停止条件和 raw/simplified 保存策略。

## 从复现到语料工程

当任务目标从“复现一个请求”扩展为“构建一批业务数据/接口语料”时，复现阶梯仍然适用，但 Green 要升级：

```text
单次 RPC Green
→ 小批量 Green
→ 分接口队列 Green
→ 窗口/限速 Green
→ 覆盖率声明 Green
```

不要把单次调用成功直接外推成可长期采集。服务端 100 页窗口、账号冷却、设备态限制、验证码、CloudWAF、TFS、HTTP 403/418 等都属于语料工程层面的红灯。
