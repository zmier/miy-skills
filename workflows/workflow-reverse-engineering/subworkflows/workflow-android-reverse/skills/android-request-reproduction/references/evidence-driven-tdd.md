# 证据驱动的逆向 TDD

## 核心原则

使用：

> 以终为始，以证据校正，以测试推进。

先定义最终可观察结果和完成证据，再从终点反推 G2、G1、交付路线、必要请求叶子和下一项最小实验。不得先执行宽范围工具操作，再事后解释它与目标的关系。

## 五层证据梯

| 层级 | 回答的问题 | 典型状态 |
|---|---|---|
| Smoke | 设备、代理、进程、Frida、类加载和脚本环境是否可用？ | `not-run/failed/blocked/passed` |
| Unit | 单个字段、算法或转换规则是否符合固定 fixture？ | `not-run/failed/blocked/passed/not-required` |
| G1 离线等价 | 同一固定输入下，外部实现是否与 App 的中间值和最终字节一致？ | `not-run/failed/blocked/passed` |
| G2 受控端到端 | 独立组装的完整请求是否被授权服务端接受？ | `not-required/not-run/failed/blocked/passed` |
| UAT 业务验收 | 最终业务现象或研究交付是否满足目标？ | `not-required/not-run/failed/blocked/passed` |

`HTTP 200` 不等于 G2 通过；必须同时检查响应正文和业务码。页面变化不能替代 G2，只能作为 UAT 或附加证据。

状态含义以 `references/acceptance-statuses.md` 为准。若预期 Red 来自课程、历史版本或外部报告，必须先在当前环境复现；未复现时记录 `not-reproduced`，而不是把备用实验写成故障修复。

执行 G2 前增加“原始成功请求预检”：用外部实现对抓包中的原始字段重算 sign、密文或关键派生值。预检失败属于 G1 首差；预检通过而外部请求被风控或环境层拒绝，属于交付环境首差。

## 红-绿-重构

每轮只推进一个当前路线上的必要红灯：

1. **Red**：登记失败测试、未知叶子或未运行关口。
2. **Hypothesis**：提出能够被证伪的最小假设。
3. **Action**：执行只改变一个关键变量的最小实验。
4. **Observation**：先记录直接观察，再解释。
5. **Green**：达到预先声明的通过证据。
6. **Refactor**：在状态保持通过时整理脚本、fixture、TASK、模板或子 Skill。

将每轮 Reason、Action、Observation、Decision 写入 `logs/LOG.md`。不能用合理解释代替 Green 证据。

## 恢复型 TDD

环境、加固和交互问题不直接改变业务算法测试，而是建立独立恢复测试：

```text
业务节点受阻
→ Recovery Red
→ 失败层假设
→ 单变量恢复实验
→ Recovery Green
→ 返回原业务节点
```

例如：

- Root 提示消失不等于请求算法通过，只表示启动 Smoke 恢复；
- Dex 被成功 dump 不等于请求链已定位，只表示静态分析输入恢复；
- RPC 输出一致不等于纯 Python 路线完成，只表示 R2 达到 `rpc-available`；
- 验证码被接受不等于登录 UAT 完成，只表示交互关口通过。

恢复 TASK 不得吞掉原始业务红灯。Green 后必须把唯一 `NEXT` 重新指回被阻塞的原节点。

## 终点反推

按以下顺序定义：

1. 写 UAT：最终希望发生什么，如何观察和归因。
2. 判断是否需要 G2：目标包含“重发”“服务端接受”或真实业务结果时必须需要。
3. 写 G1：固定哪些输入，比较哪些中间层和最终字节。
4. 选择 R1/R2/R3/R4，声明允许依赖 App、Hook、RPC 或设备到什么程度。
5. 计算该路线的必要请求叶子。
6. 从最靠近共同上游、阻止继续观察的红灯中选择下一项最小实验。

终点可以随新证据改变，但必须记录原终点、新终点、原因、受影响关口和必要叶子，不得静默漂移。

## Mermaid 控制面

`request-construction-ledger.md` 顶部 Mermaid 是工作流的核心控制面，必须同时展示：

1. **终点链**：UAT -> G2 -> G1 -> 路线门槛；
2. **请求树**：Method/URL -> Headers/Body -> 字段 -> 内部字段；
3. **取证侧枝**：未知字段 -> TASK -> 方法 -> 结果；
4. **当前路由**：唯一 `NEXT` 节点连接当前要解决的红灯；
5. **测试状态**：Smoke、Unit、G1、G2、UAT；
6. **可点击证据**：TASK、fixture、测试报告和验收记录。

图和节点表必须同步。图中出现 `passed` 而表中没有证据链接时，按未通过处理。

## 下一步选择算法

1. 若授权或 UAT 未定义，下一步是补契约。
2. 若 Smoke 失败，先修环境，不得据此否定算法假设。
3. 若目标接口未确认，先做最小因果窗口和候选验证。
4. 若不透明外层阻止读取内部字段，优先解外层。
5. 否则选择当前路线 `required` 且能力未达门槛的公共依赖。
6. 纯函数规则优先建立 Unit fixture。
7. 所有必要叶子满足后执行 G1。
8. G1 通过且目标要求真实重发时，执行一次受控 G2。
9. G2 通过后执行 UAT；UAT 不需要时按契约结束。

业务请求依赖服务端下发状态时，先按前置接口 DAG 的拓扑顺序完成 Token、设备注册和配置节点。不得直接把历史抓包中的 did/token 当作永久静态输入。

任一时刻只标记一个 `NEXT`。并行任务必须确实互不依赖，并分别标为 `NEXT-A`、`NEXT-B`。

## 完成声明

- Unit 通过：只能声明单个规则通过固定样本。
- G1 通过：只能声明算法或请求构造达到离线等价。
- G2 通过：可以声明完整请求被目标服务端接受。
- UAT 通过：可以声明预定业务或研究目标完成。

不得跨级声明。
