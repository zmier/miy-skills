# Android 目标接口分析

## 目标

把“某个动作期间抓到的一堆请求”收敛为有证据支持的目标接口。区分请求名称暗示、时间相关性和因果验证，不因 URL 看起来合理或返回 `HTTP 200` 就宣布接口已确认。

## 输入

开始前确认：

- 需求 TASK 工作区；
- 经过授权的目标行为和可观察结果；
- 至少一个边界明确的行为采集窗口；
- Reqable 会话、脱敏 HAR、fixture 或 `reqable-mcp` 数据；
- App、版本、设备和账号状态；
- 能否进行低频重放以及允许观察的业务结果。

缺少行为窗口时，返回 `capture-android-traffic`，不要直接分析整场无边界流量。

## 漏斗流程

1. 阅读 TASK 的目标边界、采集索引和工作流状态。
2. 为每个窗口记录开始、动作、结束时间和请求数量。
3. 按 `方法 + Host + Path` 归一化请求身份，将重复请求聚为一组。
4. 比较基线窗口、进入页面窗口和目标动作窗口，先排除背景流量。
5. 按 `references/funnel-method.md` 检查触发时序、窗口独占性、业务实体关联、字段语义、重复模式与响应结构。
6. 将少量候选写入 `candidate-matrix.md`，分配稳定编号 `CAND-*`。
7. 只对重点候选设计低频、单变量实验，分配编号 `EXP-*`。
8. 需要人类操作 App、读取界面状态或执行 Reqable 重放时，按 `references/human-validation-manual.md` 生成 `validation-operation-manual.md`。
9. 等待人类按手册反馈实际观察，不得代替人类填写界面结果。
10. 按 `references/replay-evidence.md` 记录重放前基线、唯一变量、操作、等待时间、刷新方式、实际观察和替代解释。
11. 将候选标记为“保留”“排除”或“仍不确定”；不要强迫所有候选二分。
12. 只有证据达到要求时，才填写 `target-interface.md`。
13. 提取脱敏 fixture，把未知字段分为静态、环境、动态和未知。
14. 更新 `handoff.md`，把唯一阻塞路由给后续 Skill。

## 编排交接

由总编排调用时：

- 接收 Mermaid 中的接口候选红灯、Green 条件和允许的验证范围；
- 每个候选实验只改变一个关键变量；
- 将候选确认结果写回请求根节点、测试矩阵和证据链接；
- 未达到 Green 条件时保持红灯，不用“高置信”替代 `passed`；
- 完成后移除旧 `NEXT`，由总编排决定进入参数归约还是补采集。

## Reqable MCP 使用顺序

优先表达分析意图，再选择实际工具：

1. 检查接收状态和采集时间范围；
2. 按时间、Host、Path、方法或关键字段列出请求；
3. 获取重点请求完整详情；
4. 按域名或 Path 聚合重复模式；
5. 比较候选在不同窗口中的出现次数和字段差异；
6. 选定目标接口后才生成重放草稿。

不得用代码生成结果代替接口确认。

## 判断规则

- URL 名称、方法名或字段名只能提高怀疑程度，不能单独确认作用。
- 目标动作后立即出现，只能证明时间相关。
- `HTTP 200` 只能证明服务器接受或处理了请求，不能单独证明业务结果。
- 重放后业务观察量变化，是较强证据，但仍需排除缓存、延迟、并发请求和自然变化。
- 重放后没有立即变化，不能直接排除候选；可能存在去重、延迟、会话状态或动态字段失效。
- 无法得到可观察业务结果时，允许输出“高置信候选”，但不得标为“已确认目标接口”。

## TASK 写回

严格按 `references/task-writeback.md` 更新需求工作区。至少写入：

- 采集窗口；
- 候选矩阵；
- 对照实验日志；
- 需要人工参与时生成的《验证操作手册》及人类反馈；
- 目标接口证据卡或“尚未确认”的结论；
- 脱敏 fixture；
- 当前唯一阻塞和下一 Skill。

不要把原始 Cookie、Token、账号、设备标识或个人信息复制到 Markdown。

## 完成标准

- A：目标接口由可重复的行为窗口和低频对照实验共同确认，且能交付脱敏 fixture。
- B：无法观察最终业务结果，但候选在窗口独占性、实体字段、时序和结构上形成一致证据，明确标记限制。
- C：未确认接口，但已把问题收敛到少量候选，并可重复说明缺少的验证条件。

只列出一批“看起来相关”的 URL 不算完成。
