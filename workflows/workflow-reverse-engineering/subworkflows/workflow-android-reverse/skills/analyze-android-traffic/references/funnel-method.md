# 漏斗式目标请求识别

## 漏斗层级

```text
完整行为窗口
→ 归一化请求组
→ 排除背景流量
→ 业务相关候选
→ 重点候选
→ 对照实验
→ 目标接口或高置信候选
```

## 第一层：限定窗口

在目标动作前开始采集，动作产生预期界面状态后立即停止。窗口过长时重新采集，不用复杂筛选弥补糟糕的实验边界。

通用窗口：

- `BASE`：不执行目标动作；
- `OPEN`：进入页面但不触发目标动作；
- `ACTION`：只执行一次目标动作。

## 第二层：请求归一化

按以下身份聚类：

```text
HTTP 方法 + Host + Path
```

查询参数和请求体作为同组内差异，不把动态参数不同的同一路径列成多个候选。

## 第三层：背景排除

优先排除：

- 静态资源、图片、媒体分片；
- 配置、版本检查和网络探测；
- 广告、通用日志、崩溃上报；
- 基线中同频出现的心跳和保活；
- 与目标实体无关联的重复请求。

“日志”或“心跳”只是初步标签。如果它只在目标动作出现且包含目标实体字段，仍应保留为候选。

## 第四层：候选特征

逐项记录，不机械计算总分：

| 维度 | 需要观察的证据 |
|---|---|
| 时序 | 是否紧邻目标动作 |
| 独占性 | 是否只在 ACTION 出现或显著增加 |
| 实体关联 | 是否包含目标 ID、分集 ID、会话或状态 |
| 语义 | Host、Path、字段和方法是否与动作相容 |
| 重复模式 | 是否随动作次数、播放阶段或页面生命周期变化 |
| 响应 | 状态码、响应结构和错误是否可解释 |
| 可重放性 | 能否构造低频、最小实验 |

## 第五层：候选矩阵

候选矩阵必须同时呈现支持证据和反证。使用：

- `保留`：值得进入实验；
- `排除`：已有明确反证；
- `仍不确定`：证据不足或无法实验。

不要为了减少数量而把不确定项伪装成排除项。
