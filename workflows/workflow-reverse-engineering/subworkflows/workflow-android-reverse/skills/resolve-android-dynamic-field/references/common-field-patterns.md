# 常见动态字段模式

## 多来源稳定标识

典型结构：

```text
内存
→ 持久化
→ 来源 A
→ 来源 B
→ 系统标识
→ 安装 UUID
→ 规范化、哈希或编码
```

处理重点：

- 按代码顺序记录来源优先级；
- 分别记录“当前设备采用分支”和“所有可用分支”；
- 检查权限、系统版本和设备能力为何让某些来源为空；
- 替代来源能生成格式正确的值，不等于还原当前设备真实值；
- 验证 `source → Python → App/Persisted`。

Day18 `Buvid` 属于此模式。

## 持久化会话随机值

典型结构：

```text
进程初始化随机字节
→ 固定宽度编码
→ 主进程写入 SharedPreferences
→ 请求阶段重复读取
```

处理重点：

- 区分每请求、每进程、每会话和每安装生命周期；
- 检查是否仅主进程负责写入；
- 十六进制必须使用 `%02x` 或 `bytes.hex()` 保留前导零；
- 当前值、静态 fallback 和持久化值应分别取证；
- 不因字段可删除就跳过生成链结论，必要性和可生成性是两个维度。

Day18 `session_id` 属于此模式。

## 复合设备指纹

典型结构：

```text
稳定设备输入
+ 动态采集 map
+ 时间
+ 随机字节
→ 哈希/拼接
→ checksum
→ 持久化或服务端同步
```

处理重点：

- 请求读取链和首次生成链必须分开；
- Kotlin 顶层采集函数、接口实现和 JADX 展示别名需要确认真实符号；
- map key 只作为线索，必须读取采集函数或运行时真实值；
- 时间、随机数和 UUID 必须成为外部实现的可注入参数；
- 用同一次 App fixture 做确定性比较；
- local 与 remote 字段即使当前相等，也要分别说明来源和签发边界。

Day18 `fp_local` 属于此模式。

## 输出要求

无论属于哪种模式，都至少回答：

1. 当前请求读到的值来自哪一层？
2. 前面各层为空时，首次生成如何选择分支？
3. 值的稳定周期是什么？
4. 外部实现需要哪些声明输入？
5. 当前结论是读取、替代、真实重建还是服务端认可？
