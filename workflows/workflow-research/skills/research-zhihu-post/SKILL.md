# Research Zhihu Post

状态：`structural-green / source-case-tested / independent-forward-test-pending`

## 定位

把“写知乎贴”同时当作两件事：

```text
对外输出：写成陌生同行能独立理解、可以参与讨论的研究稿；
对内审计：借助外部视角暴露隐含前提、过期结论、术语依赖和证据跳步。
```

不要把它降格为宣传文案，也不要把清楚易读误解为删掉方法和边界。目标是让读者不读取项目目录、不认识 TASK 编号，也能判断：研究发现了什么、怎么发现、排除了什么、仍不知道什么。

本 Skill 是 `workflow-research` 的研究解释与反思执行单元。它不替代论文写作、`research-brainstorm`、`research-roadmap`、`miy-mail` 或 `task-driven-project-manager`。

## 模式路由

先明确模式，不要让“知乎风格”自动等于“允许公开”。

| Mode | 用途 | 是否面向外部 | Green 标准 |
|---|---|---:|---|
| `outside-view-audit` | 默认；项目组借陌生读者视角复盘 | 否 | 解释稿可独立理解；隐含知识与过期结论已暴露；问题回写项目 |
| `peer-discussion-draft` | 给同行、老板、coauthor 或研讨会讨论 | 待审核 | 证据、方法和开放问题完整；完成脱敏；明确非公开状态 |
| `publish-ready` | 用户明确要求准备发布或同步平台 | 是 | 通过事实、可读性、保密与平台格式检查；获得用户发布意图 |

用户只说“写一篇知乎贴”时，默认交付 `peer-discussion-draft`，不得替用户发布。只有用户明确要求发布、同步或覆盖线上文档时，进入 `publish-ready` 的平台动作。

## 最小输入

开始前尽量收集：

- 本轮证据截止日期；
- 当前最稳的经验事实；
- 最新模型、样本、单位、结果表与统计口径；
- 已被削弱、修正或归档的旧解释；
- 数据和识别边界；
- 当前下一步及其依赖的数据或决策；
- 旧版知乎稿或同行稿；
- 目标读者和公开/内部边界。

输入分散在多个 TASK 时，先建立简短的 `evidence reconciliation`，不要直接从记忆写稿。

## 核心工作流

### 1. 冻结版本与受众

记录：

```text
evidence cutoff
target reader
mode
source draft
destination artifact
publication/sync permission
```

旧稿更新时，先比较旧稿的证据截止日期与当前项目状态。

### 2. 重建当前证据状态

把来源材料分成五栏：

| 状态 | 要回答什么 |
|---|---|
| current anchor | 现在最稳的事实是什么 |
| location / scope | 结果发生在哪个单位、样本、时间和尺度 |
| negative evidence | 哪些直觉解释没有通过检验 |
| superseded claim | 哪些旧表述已被修正、降级或推翻 |
| unresolved / next | 还不知道什么，下一步由什么证据决定 |

如果旧稿存在 `superseded claim`，必须重写对应正文。不要只在文章末尾追加“最新更新”，让过期结论继续占据主叙事。

### 3. 清理私有知识依赖

扫描并处理：

- TASK / subtask 编号；
- 未解释缩写、英文变量和内部黑话；
- 私有路径、账号、协作者姓名和敏感字段；
- 只有项目成员才知道的样本口径；
- “这个”“上面”“之前发现”等无独立指向的表达。

正文用完整中文概念。任务号只在确有追溯价值时放到文末内部索引，不承担解释职责。

### 4. 按研究逻辑重写

优先采用：

```text
研究问题
-> 白话版当前结论
-> 关键概念与数据单位
-> 初始发现
-> 逐层排查与结论修正
-> 没有解释成功的路线
-> 当前可说 / 不可说
-> 下一步
-> 可回答的同行问题
```

不要按 TASK 时间流水账组织正文。TASK 记录“做了什么”，知乎稿解释“这些工作怎样改变了我们对问题的认识”。

需要模板时使用 [`assets/research-zhihu-post-template.md`](assets/research-zhihu-post-template.md)。

### 5. 分开四层结论

每个核心结果都检查：

```text
统计事实：系数、方向、区间、p 值或不确定性是什么？
经济含义：单位、尺度、典型单元和绝对总量怎样解释？
机制相容：与哪些故事相容，又与哪些故事冲突？
因果结论：当前设计是否真的支持“X 导致 Y”？
```

禁止用星号替代机制，也禁止用“匹配后显著”“加入固定效应后显著”自动升级因果语言。

### 5.5 公式与白话双层表达

只要核心结论依赖回归、匹配、事件研究、分解式、统计检验或识别假设，就在对应证据段落采用双层表达：

```text
同行快速层：用 LaTeX 公式压缩呈现估计对象、比较组、时间和可证伪条件；
网友解释层：紧跟公式逐项翻译“在比谁、扣除了什么、什么结果支持猜想、仍不能推出什么”。
```

公式不能只堆在文末 Q&A，也不能替代自然语言。每个承担核心结论的公式，至少说明：

- 观察单位和时间下标；
- 结果变量、处理变量或比较组；
- 回答前控制变量、固定效应和标准误聚类层级；
- 被估计的系数、差值或原假设；
- 系数的单位、是否经过对数等变换，以及普通读者应怎样理解；
- 当前设计能够排查什么，不能据此升级为什么因果或机制结论。

执行 `specification-result binding`：公式、结果表和正文必须属于同一个估计规格。主规格与稳健性规格分别写清，不能把稳健性规格的固定效应写进公式，却在表中报告主规格系数。公式后用一句话明确“下表数字来自哪一个规格”。

方法名称必须与实际程序一致：精确分组内最近邻匹配、倾向得分匹配、加权、固定效应回归等不得互相代称。匹配结果要解释匹配规则和配对估计量，并明确它只能处理已观测差异，除非设计另有识别依据。

遇到层级分解时，分开呈现：

```text
原始量上的定义或算术恒等式；
变换后结果变量所进入的回归；
真正回答“层级是否不同”的系数差或联合检验。
```

原始量可以相加，不代表对数回归系数可以当作贡献率相加；两组都有星号，也不代表两组系数彼此显著不同。若正文声称存在层级、组别或方向差异，必须给出正式差异检验。

默认使用 `$$...$$` 写块级 LaTeX。同步平台后必须回读公式；特别检查导入器是否把换行两侧拼成错误命令，例如把 `\qquad` 与下一行普通字母拼接。优先把命令及其后续参数写在同一行，避免依赖 Markdown 到平台公式转换器的空白保留行为。

### 6. 运行陌生读者审计

读取并执行 [`references/outside-reader-audit.md`](references/outside-reader-audit.md)。至少完成：

- `zero-private-context test`：不读内部文档能否理解；
- `term-definition test`：术语是否在首次出现时解释；
- `evidence-update test`：旧结论是否按新证据重写；
- `claim-ladder test`：事实、位置、机制、因果是否越级；
- `number-and-unit test`：样本、单位、星号和口径是否可解释；
- `formula-specification binding test`：公式、结果表、方法名称和报告系数是否属于同一规格；
- `confidentiality test`：是否暴露不应离开项目的信息。

若读者必须知道内部 TASK 才能理解，审计不通过。

### 7. 回写研究系统

知乎稿不是孤立产物。根据稿件暴露的问题回写：

- `research-roadmap`：链接最新解释稿，并更新被修正路线；
- `TASK00` / route portfolio：登记新困惑、降级解释和下一数据 Gate；
- `research-brainstorm`：把同行问题作为下一轮共同 brief 的输入；
- evidence owner：修正文档中与当前结论冲突的表述；
- `miy-mail`：需要向特定对象沟通时，再适配为邮件，不直接复制整篇。

仅当知乎稿发现源证据文档确有错误时才改 evidence owner；不要让传播稿反过来篡改原始结果。

### 8. 同步与验证

用户要求同步飞书、知乎草稿箱或其他平台时，读取对应平台 Skill。更新既有文档时优先覆盖既定现行版本，除非用户明确要求另存为新版本。

同步后回读验证：

- 标题和目录；
- 核心结论段；
- 表格中的单位与星号；
- LaTeX 公式；
- 公式、结果表和正文是否绑定同一估计规格；
- 被降级的旧解释；
- 下一步和开放问题。

## 输出契约

推荐文件名：

```text
outputs/research-zhihu-post.md
outputs/research-zhihu-post-audit.md       # 仅复杂更新时需要
```

已有稳定稿件名称时沿用，不为每次更新创建新文件。文首至少标明：

```text
状态 / mode
证据截止日期
因果与公开边界
```

正文至少包含：白话结论、数据与单位、证据演进、负证据、当前边界、下一步、同行问题。核心结论依赖计量模型或统计分解时，还应包含就地放置的公式、逐符号解释和对应的普通读者翻译。

## 与相关能力的边界

| 能力 | 语义 owner |
|---|---|
| 完整的知乎式研究解释与外部视角审计 | 本 Skill |
| 子任务执行者的轻量 `peer-brief.md` | `task-driven-project-manager` |
| 多角色提出和批评候选机制 | `research-brainstorm` |
| 可点击研究演进与状态导航 | `research-roadmap` |
| 写给特定收件人的行动型沟通 | `miy-mail` |
| 正式论文叙事与投稿文本 | `workflow-paper` |

子任务 `peer-brief` 只解释一个局部工作包；当需要整合多个 TASK、重写研究主叙事、更新实际知乎稿或进行项目级外部视角审计时，切换到本 Skill。

## 完成检查

- 陌生同行能否用三句话复述研究问题、当前发现和最大限制；
- 是否解释了分析单位、时间关系和关键变量；
- 是否同时呈现支持证据、负证据和被修正的旧路线；
- 是否区分统计显著、经济意义、机制相容和因果；
- 核心公式是否就地出现，且同行能快速识别估计量、网友能用自然语言复述比较逻辑；
- 公式、结果表和文字是否来自同一规格，方法名称是否准确；
- 是否避免 TASK 编号、缩写和私有路径承担正文逻辑；
- 是否说明下一步为何值得做以及什么结果会改变路线；
- 是否保留明确的公开/内部边界；
- 若同步平台，是否已回读关键内容。

任何一项失败都应先修稿，不要把“文章已经很长”当作完成标准。
