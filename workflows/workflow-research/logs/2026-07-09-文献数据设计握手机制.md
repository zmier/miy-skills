# 文献-数据-设计握手机制

## 来源案例

```text
/Users/narra/Documents/alib/Writer/03 Projects/260521-基金经理研究
```

本日志记录 `CASE-260521-基金经理研究` 对 `workflow-research` 的一次真实项目反哺。该案例先完成强参考文献阅读与研究路线拆解，再基于核心数据判断外部数据需求，随后由数据侧探索 CSMAR/RESSET、下载 P0/P1 数据、交付字段字典/QC，最后由研究侧锁定研究设计。

## 原始问题

用户在案例推进后提出：

```text
我们本次先做文献、核心数据，然后去 CSMAR 探索并下载补充数据，
再基于数据和文献设计实验。这个过程有什么经验可以反哺 workflow-research？
是否应该开子 SKILL？
比如最好有两个同学配合：一个获取数据的同学，一个研究设计的同学，
两个人通过 miy-mail 来沟通？
```

## 当时判断

这次案例暴露出 `workflow-research` 目前缺少一个稳定协议：

```text
强参考文献
→ 初始变量 / 识别 / 机制需求
→ 核心数据盘点
→ 外部数据库 opportunity scan
→ 数据侧 first-pass / 字典 / QC
→ 研究侧 scope-lock
→ 数据侧 processed panel
→ 研究侧 acceptance
→ research design v1
```

这个发现不是单纯的项目管理，也不是单纯的数据工程。它位于 R2 文献定位、R3 数据可得性和 R4 研究设计的交界处。

## 方案分歧

### 方案 A：直接创建子 Skill

候选名称：

```text
skills/research-data-design-handshake/SKILL.md
```

优点：可调用、职责清晰。  
风险：当前只有一个真实案例，若立即创建子 Skill，可能把个案协作模式误写成通用规则。

### 方案 B：只留在项目 TASK

优点：不污染 workflow。  
风险：方法论价值较高，如果只留在 TASK 邮件和日志里，下次研究项目很难复用。

### 方案 C：先写 workflow log + reference + templates

优点：保留原始问题形状，同时把较稳定的流程、角色和验收标准沉淀为可复用材料。  
风险：还不是完整子 Skill，需要下个案例 forward-test 后再升级。

## 最终决定

采用方案 C。

## 稳定规则草案

`workflow-research` 需要承认一种研究项目协作协议：

```text
research-side ↔ data-side handshake
```

其中：

- 研究侧负责把文献中的变量、机制、识别和样本需求转译成数据需求。
- 数据侧负责把数据库可得性、字段、代码字典、覆盖、QC 和 processed table 交付为可 review 资产。
- `miy-mail` 负责保存双方协议、回复、scope-lock、acceptance 和下一步，避免需求漂移。
- `task-driven-project-manager` 负责执行层 TASK、日志、产物和 evidence。
- `workflow-research` 负责判断这些数据交付如何改变 route portfolio、claim、design、threat 和 paperization。

## 不提升为稳定主流程的内容

以下内容仍留在案例或模板中，不写入 `workflow-research/SKILL.md` 默认主流程：

- CSMAR/RESSET 作为固定数据库；
- `FDSHRCHG StatPd=3` 作为固定 flow 口径；
- 数据侧同学和研究侧同学的具体称呼；
- 邮件文件名、时间戳和本项目路径；
- 基金经理研究的具体变量清单。

## 迁移边界

当前状态：

```text
structural-green / forward-test-pending
```

可以迁移的部分：

- 文献启发的数据需求应进入可执行数据请求；
- 数据交付必须带字段字典、代码字典、QC、coverage 和 provenance；
- 研究侧必须显式 review，给出 accepted / accepted-with-exceptions / blocked；
- scope-lock 先于 full-download 铺开；
- `miy-mail` 可作为研究侧与数据侧的 correspondence ledger。

仍需 forward-test 的部分：

- 是否适用于非金融数据库；
- 是否适用于单人研究项目；
- 是否适用于没有明确“数据同学”的项目；
- 是否应该升级为正式子 Skill。

## 后续观察点

下一个研究项目若出现类似场景，观察：

1. 是否自然需要数据侧 / 研究侧双角色分工；
2. 数据 request email template 是否能减少反复补问；
3. delivery review memo 是否能稳定产生 scope-lock；
4. tracker 是否能防止“数据已下载但研究设计仍无法推进”；
5. 是否足以把候选子能力升级为 `skills/research-data-design-handshake/`。
