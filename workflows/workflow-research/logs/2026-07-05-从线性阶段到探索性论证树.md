# 从线性阶段到探索性论证树

## 来源

本日志来自 `CASE-260521-基金经理研究` 在数据回流后准备进入研究设计阶段的讨论。

当时 `workflow-research` 父入口使用了 R0-R7 的“研究项目主轴草案”：

```text
R0 项目界定
R1 研究问题
R2 文献定位
R3 数据可得性
R4 研究设计
R5 论证链
R6 paper 化
R7 交付与反哺
```

讨论中发现，这种编号和排序有助于导航，但可能产生过强的线性阶段暗示，不能准确描述探索性学术研究的真实推进方式。

## 用户原始困惑

用户指出：

> 但其实我们目前只是弄好了数据、确定了要研究「基金」。其他几个R似乎还没做。此外，R1-R7并不是完全线性的对吧？感觉学术研究更像是一种探索性的？目前这样用R1-R7排序，是否合理呢？

随后用户进一步补充：

> 对！比如我们目前看似最完善的「R3数据」，后面肯定还是要基于研究内容的设计，而补充很多数据的。比如：可能要补充CSMAR中的基金数据等。所以我觉得用1-7这种命名有点线性暗示。此外，目前的阶段划分也未必合理吧...我反而觉得，一个大research应该是包含了很多分型的小research的结构：为了论证A，需要论证A1（找数据、读文献、做实验），也需要找数据、读文献、做实验。最后应该是很多个子实验/论证的组合。至于要用谁做主轴（树干），谁做树枝，往往最后才能定，要考虑很多：期刊偏好、问题热点等等。我不知道我表达的是否清晰，请帮我总结下我的困惑

## 当时的总结

这段困惑不是在纠结命名，而是在质疑 `workflow-research` 目前的研究观是否过于“线性工程化”。

用户的核心观点可以概括为：

```text
学术研究不是按 R1 -> R2 -> R3 -> R4 -> R5 -> R6 -> R7 单线推进的工程；
它更像一个探索性论证树 / 候选路线组合系统。
```

真实研究更像：

```text
一个大 research 里包含很多小 research；
每个小 research 都可能同时需要问题、文献、数据、设计、实验、论证；
最后哪些成为主线，哪些成为支线，往往不是一开始就能决定。
```

## 关于“R3 数据”的修正

本案例中，支付宝基金经理问答 SQLite 已经回流，看似 `R3 数据可得性` 最完善。但这只能说明：

```text
当前有一块可用的核心语料资产。
```

它不能说明整个研究项目的数据已经完成。

一旦研究问题和识别设计具体化，仍可能需要补充：

```text
CSMAR 基金数据；
基金净值、收益和风险；
基金规模和资金流；
基金经理履历；
基金公司特征；
市场行情；
基金公告；
平台曝光或关注度；
事件窗口数据。
```

因此，`R3` 不应被理解成“数据阶段完成”，而应被理解成“每条候选论证链都要持续维护的数据工作面”。

## 关于阶段模型的修正

R0-R7 可以保留为检查维度，但不应作为硬顺序。

更准确的表述：

```text
R0-R7 是研究项目的检查面板，不是顺序关卡。
```

它们之间会反复迭代：

```text
数据 R3 反过来改变研究问题 R1；
文献 R2 反过来重写项目界定 R0；
研究设计 R4 暴露数据缺口，回到 R3；
论证链 R5 发现贡献不成立，回到 R1/R2；
paper 化 R6 发现目标期刊不匹配，回到 R2/R4。
```

所以，排序作为导航有用，但作为流程可能误导。

## 子研究 / 子论证模型

用户提出的更自然单位不是“阶段”，而是：

```text
候选 claim / 子论证 / 子实验 / research route
```

例如，为了论证 A，可能需要论证：

```text
A1：投资者确实在问某类问题；
A2：基金经理回应存在选择性；
A3：回应内容具有信息 / 安抚 / 营销特征；
A4：互动与资金流或持有行为有关；
A5：这种关系不是由基金业绩或市场行情共同驱动。
```

每个 A1-A5 都有自己的：

```text
问题；
文献；
数据；
变量；
识别；
实验；
稳健性；
替代解释。
```

因此，一个大 research 更像论证树，而不是任务流水线。

## 主轴和树枝的后验性

一开始很难知道谁是主轴、谁是树枝。主线选择往往取决于后验因素：

```text
数据是否足够干净；
识别是否可信；
文献 gap 是否真实；
结果是否有意思；
期刊偏好；
政策或学术热点；
导师取向；
可写性和贡献强度。
```

所以 workflow 不应过早要求“先定主轴”。更合理的是保留多个候选子研究，让它们竞争、合并、降级或拆分。等证据、文献和结果逐渐出来后，再决定：

```text
哪条是 paper 主干；
哪条是机制；
哪条是 robustness；
哪条只是附录；
哪条应该放弃；
哪条可以拆成另一篇 paper。
```

## 对 workflow-research 的架构含义

这次讨论提示：`workflow-research` 的主轴可能应从“线性阶段模型”转向“探索性论证树 / 候选路线组合模型”。

一个可能的新抽象：

```text
Research Project
→ Candidate Claims / Research Routes
→ 每条 route 内部有：
   question / literature / data / design / evidence / threat / contribution
→ route 之间竞争、合并、降级、拆分
→ 最后 paper 化
```

R0-R7 仍可保留，但应改写为每条 route 或整个项目的“诊断面板”：

```text
Project-level panels:
  project boundary / portfolio / paperization / delivery

Route-level panels:
  question / literature / data / design / evidence / threat / contribution
```

## 当前暂定规则

迁移状态：`draft-rule`。

可以先形成以下草案规则：

1. 不把 R0-R7 表述为线性阶段，而表述为诊断面板或工作面。
2. 研究项目的基本单位可以是 `research route` / `candidate claim`，而不是 TASK 或阶段。
3. 每条 route 自带文献、数据、设计、证据、威胁和贡献检查。
4. 研究项目管理应允许多条 route 并行探索、竞争、合并、降级和拆分。
5. paper 化阶段不是简单末端步骤，而是把 route portfolio 重组为可投稿论文结构的过程。

## 暂不直接提升的内容

本讨论暂不直接改写 `SKILL.md`，因为还需要至少一次真实项目 forward-test。

建议先在 `CASE-260521-基金经理研究` 中用该模型试跑：

```text
候选 route 1：投资者问什么；
候选 route 2：基金经理回应选择性；
候选 route 3：回应内容是信息还是说服；
候选 route 4：互动与资金流 / 持有行为；
候选 route 5：压力期沟通与耐心资本。
```

每条 route 都建立：

```text
claim；
需要的文献；
已有数据；
待补数据；
可行设计；
识别威胁；
可能贡献；
当前状态。
```

如果该试跑能显著改善研究推进，再把该规则提升到：

```text
references/research-route-portfolio.md
templates/research-route-card-template.md
SKILL.md 的主轴表述
```
